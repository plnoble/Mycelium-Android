## Keystore（补充任务书二第 3 项更正）

- 上一版「清除数据后密钥仍存在」的结论**作废**——那是探针「有则取、无则新建」逻辑造成的假象（清除后探针自动新建了同别名密钥并重新包装，日志无法区分）。
- 按要求重做（清除前导出密文 → `pm clear` → 启动后、新建任何密钥**之前**先查别名）：实测 **alias_exists_before_any_create=false**，即清除应用数据会**删除 AndroidKeyStore 密钥**；旧密文自然无法解包（unwrap_old_ciphertext=null）。不可恢复是**预期且符合安全直觉**的行为，本条记录为最终结论。

## SQLite 中文代表性检索（补充任务书二第 4 项）

- 200k 行中文行（每行约 250 字节，约 50 MB 行数据）；查询词「量子纠缠退相干」只命中 2 行（已验证命中数=2），带 LIMIT 20。
- LIKE（`s LIKE '%量子纠缠退相干%' LIMIT 20`）与 trigram MATCH（`MATCH '量子纠缠退相干'` COUNT）同一查询对照：

| 方案 | insert 200k | LIKE（LIMIT 20） | trigram MATCH | 测试库大小 |
|---|---|---|---|---|
| 系统自带（无 FTS5） | 1,520 ms | 419 ms | 不可用 | 68.5 MB |
| androidx bundled | 1,649 ms | 199 ms | 3,540 ms | 184.5 MB |
| SQLCipher | 2,290 ms | 232 ms | 4,168 ms | 190.5 MB |

- 说明：MATCH 计时包含建 trigram FTS 表 + 200k 行索引入库 + 查询（一次性的索引建造成本）；LIKE 是全表扫。查询命中极少时 LIKE 也不慢——**trigram 优势在索引可复用**：每次重扫全文 200ms 级 vs 建索引 3-4s 一次性。

## 之前的差别怎么解释（补充任务书一第 4 条）

- 10-06 的 2.6 t/s 与 8.1 t/s 不是矛盾：本次固定条件（屏亮、线程显式、每指标 3 次）下，9B@6 的三次 256 token 生成是 **1.19 / 1.34 / 4.70 t/s**——同一设定内就出现近 4 倍的波动。设备在持续负载下存在明确的性能调度/热治理波动（电池 40-43°C 区间），旧两个数字同属这类波动；叠加旧测时线程未显式设置、屏幕休眠状态不明，无法进一步归因。
- 屏幕休眠确实会停住加载/生成（10-06 已观察），本次用保屏标志排除。
- 结论：9B 在同一次测量内的波动 > 线程档差异；按「每指标 3 次」记录的三个数字使用户与后续工程对波动有直观预期。

## 推荐（补充任务书一第 9 条）

- **伴侣默认模型：Qwen3.5-4B-Q4_K_M（4B），线程档 6**。理由：四参数重编后 4B@6 生成 7.77-8.17 t/s、约为 9B@6（4.6-4.7 t/s）的两倍且三连稳定；9B 速度波动与「连续跑消失」在上游文档参数构建下已解决，可作需要更强回答时的备选。
- **默认后端：CPU（线程档 6）**。理由：OpenCL 编不通（见上）；4B 用 6 线程比 4 线程快 ~48%（gen256 8.73 vs 5.90）。
- **数据库：SQLCipher（统筹裁决）**。理由：总计划要求伴侣与圆桌两个空间都用加密库；实测 SQLCipher 支持 FTS5 与 trigram，写入与查询比不加密慢一些但可接受。系统自带 SQLite 无 FTS5，不选。
