# P2-2b 发版准备：自动检查更新、应用内下载校验安装、补全发版流程（做完发 0.4.0）

- 仓库 / 基准提交：安卓仓库 `main`（P2-2 合并后）
- 分支：`wp/P2-2b-release-ready`
- 工作目录：`D:\Agent\Project\Nivra`
- 依赖：P2-2 已合并。
- 规模：3–5 个工作日。
- 背景：
  - 用户 2026-10-18 定：P2-2 合并后先做这个包，做完发 **0.4.0**，作为第一个正式版。以后每合并一个功能包发一个小版本，靠应用内更新送到手机上，不再用数据线装。
  - 现在的样子：
    - 手机上装的正式版是 0.1.1（versionCode 2）。0.2.0、0.3.0 都没发过。本地 `main` 是 0.3.0（versionCode 4）。
    - 应用里只有「我的 → 检查更新」一个手动按钮。有新版时，它用浏览器打开 APK 地址（`MyceliumApp.kt` 的 `UpdateText`）。没有自动检查、应用内下载、校验，也不会调起安装。`docs/UPDATE_ARCHITECTURE.md` 规划的 ApkDownloader / ApkVerifier / PackageInstallerLauncher 都还没做。
    - 网关 `OutboundGateway` 有两个限制：
      - 只会把响应当成文本整段读进内存；
      - 不跟随重定向（`instanceFollowRedirects = false`）。

      GitHub 的 APK 下载地址会 302 跳到另一个域名，近来是 `release-assets.githubusercontent.com`，以实测为准。这个域名不在 `Update` 白名单里。
    - `release.yml`：
      - 打标签触发；
      - 检查标签和 versionName 一致；
      - 签名后发布 APK 和 `.sha256`；
      - 发布说明是 GitHub 自动生成的英文提交列表。

      P2-1b 加的 NDK 和 llama.cpp 准备步骤**从没在 GitHub 上跑过**。
    - 本地正式包约 55 MB。其中 SQLCipher 带了 4 种 CPU 架构的库，而本地模型引擎本来就只编 arm64-v8a。

## 目标（用户能得到什么）

- **有新版时的升级流程**：
  1. 「我的」上出现一个不打断的提示；
  2. 点进去，能看到这一版的中文更新说明和安装包大小；
  3. 点「下载并安装」，看着进度下完，App 自动校验；
  4. 系统弹出安装确认，点「安装」就升级好了，数据都在。
- **不想升级时**：
  - 可以选「忽略这个版本」；
  - 也可以在设置里关掉自动检查，只用手动按钮。
- **发版本身**：对统筹和用户来说只剩三件事：改版本号、写更新说明、打标签。下面这些情况，流程会自己拦住：
  - 签名不对；
  - 版本号没涨；
  - 更新说明没写。

## 步骤

1. **网关能下载文件**（`:net`）：
   - **写文件**：新增按流写文件的下载，不把内容读进内存；给调用方进度，可以取消。
   - **断点续传**：中断后再试，从已经下好的地方接着下（服务器支持 Range 时）；不支持就从头下。
     - 跳转后的地址会过期，所以续传时要从原始地址重新走一遍跳转。
     - 续传出来的文件 sha256 对不上时，删掉，从头再下一次。
   - **重定向**：跟随，但**每一跳都重新过白名单**，用途不变；最多跳 5 次；只许 https；跳到白名单外照样拒绝。
   - **审计**：每次下载记一条：时间、每一跳的域名、用途、大小、状态。不记内容。
   - **白名单**：`Update` 用途补上 GitHub 下载实际跳到的域名。**开工时用真实的 v0.1.1 发布 APK 地址实测跳转链**，交付报告写明实测日期和结果。
   - **做成通用的**：P2-5 下载模型会直接复用，那边只需要加用途、白名单和前台服务。
2. **读发布信息**（`GitHubReleaseClient`）：
   - **按名字找资产**：找 `mycelium-v<版本>.apk` 和 `mycelium-v<版本>.apk.sha256`，不再取「第一个 .apk」。同时记下大小和发布说明（`body`）。
   - **缺资产时**：缺 APK 或缺 `.sha256` 的发布，只显示「有新版本」和发布页链接，不提供应用内安装。
   - **错误说人话**：连不上、格式不认识、GitHub 限流（403 / 429，提示「检查太频繁，稍后再试」）。不再把 `GitHub returned HTTP 403` 这类原文给用户看。
3. **自动检查**：
   - **什么时候查**：打开 App 时检查；距上次检查不到 24 小时就不查。检查在后台进行，不挡界面。失败时不打扰，错误只在手动检查时显示。
   - **设置**：「我的」里加开关「自动检查更新」，默认开；显示「上次检查：……」；手动按钮保留。
   - **有新版时**：
     - 底栏「我的」上出现一个小红点；
     - 「我的」页顶部出现一张卡片，内容有版本号、大小、更新说明（纯文本显示，太长可以展开），两个按钮「下载并安装」「忽略这个版本」；
     - **不弹窗**。
   - **忽略**：忽略某个版本后，不再提示它；出了更新的版本再提示。
   - **不做**：后台定时检查、自动下载（安装包几十 MB，可能用的是流量）。
   - **存储**：上次检查时间和忽略的版本，用普通偏好存储就行（不是个人数据）。
4. **下载和校验**：
   - **空间**：下载前查可用空间（安装包大小加余量），不够就拦下，说清楚差多少。
   - **下载过程**：
     - 存到缓存目录 `updates/`（`file_paths.xml` 里已经有）；
     - 显示进度，可以取消；
     - 离开这个页面，下载继续；App 被关掉就停，下次接着下。不用前台服务。
   - **校验**：下完依次核对四项：
     1. sha256 和发布里的 `.sha256` 文件一致；
     2. 包名和当前 App 一致；
     3. 签名证书和当前装着的 App 一致（`GET_SIGNING_CERTIFICATES`）；
     4. versionCode 比当前的大。

     任何一项不对：删掉文件，用人话说明是哪一项，不安装。
   - **清理**：安装成功或放弃以后，清掉 `updates/` 里的文件；启动时也清一次过期文件。
5. **安装**：
   - **安装方式**：用 `PackageInstaller` 会话安装（`ACTION_INSTALL_PACKAGE` 已弃用）。遇到「需要用户确认」的状态，就把系统的确认界面拉起来。成功、失败、用户取消，都要有结果提示。
   - **「安装未知应用」**：还没允许时，先说明为什么需要，再带用户去系统里的这个设置页。只带过去，开不开由用户决定；回来以后接着装。
   - **调试包**（包名带 `.debug`）：不自动检查，也不提供安装。GitHub 上的是正式包，装上会变成另一个 App。手动检查仍可显示有没有新版。
6. **发版流程**（`release.yml`；检查逻辑写成脚本 `scripts/release-guard.sh` 由流程调用，方便在本地演示）：
   - **发布说明**：改用仓库里的中文文件 `docs/releases/v<版本>.md`（`body_path`），文件不存在就中止。去掉自动生成的英文提交列表。
   - **versionCode**：必须比上一个标签里的大，不然中止。为此要拉完整历史。
   - **签名指纹固定**：
     - 把 0.1.1 签名证书的 SHA-256 指纹写进仓库。指纹是公开信息，不是密钥。
     - 指纹从 GitHub 上 v0.1.1 发布的 APK 里用 `apksigner` 取，交付报告写明来源和指纹值。
     - 构建后用 `apksigner verify --print-certs` 比对，对不上就中止。
   - **手动试跑入口**（`workflow_dispatch`）：
     - 照常签名打包、比对指纹、算 sha256；
     - **不发布、不上传 APK**，只在日志里打出版本号、sha256 和指纹。

     用途：第一次推送后，用它验证 GitHub 上能编出带 llama.cpp 的签名包。
7. **正式包只带 arm64-v8a**：
   - 本地模型本来就只支持 arm64；
   - SQLCipher 的其他架构库只从正式包里去掉，调试包和测试包不变（模拟器还要用）；
   - 交付报告写正式包改前、改后的大小。
8. **发布说明、版本号、发版文档**：
   - **发布说明**：写 `docs/releases/v0.4.0.md`，中文，写给用户看：
     - 这一版能做什么：圆桌、炉边人物、本地和云端模型、应用内更新；
     - 已知问题，例如本地模型第一轮回答慢。
   - **版本号**：改成 0.4.0、versionCode 5。**不打标签，不推送。**
   - **发版步骤文档** `docs/RELEASING.md`：一页纸，给统筹和用户看。顺序是：改版本号 → 写说明 → 合并 → 推送 → 看 CI → 试跑发布流程 → 打标签 → 看发布 → 手机上验证。
   - **更新架构文档**：`docs/UPDATE_ARCHITECTURE.md` 改成中文，写成实际的做法。
9. **公开内容检查脚本** `scripts/check-public.ps1`（统筹推送前跑）：
   - **扫描范围**：
     - HEAD 的所有被跟踪文件；
     - `origin/main..HEAD` 每个提交的改动（只在历史里出现也算）。
   - **一定失败的**：
     - 私钥和密钥样式：`-----BEGIN … PRIVATE KEY`、`sk-` 开头的长串、`hf_`、`ghp_` / `github_pat_` 等；
     - 带用户名的路径：`C:\Users\<名字>\`、`/home/<名字>/`、`/Users/<名字>/`；
     - 被跟踪的 keystore、`*.gguf`、`*.apk` 文件。
   - **本地补充词表**：
     - 从一个**不进仓库**的文件读，例如 `.local/public-denylist.txt`，并把它加进 `.gitignore`；
     - 用户名、设备序列号这类词，由统筹自己往里写；
     - 脚本和仓库里都不出现这些词本身。
   - **只列出、不失败的**：其他本机盘符路径（`D:\…` 之类），交给统筹逐条看。
   - **自测**：脚本带自测，用造出来的违规样例跑。

## 范围

- **可以改**：
  - `:net`（下载、重定向、白名单）；
  - app 的 `update/` 和「我的」页、`AndroidManifest`；
  - app 的版本号和正式包架构设置；
  - `.github/workflows/release.yml`；
  - `scripts/release-guard.sh`、`scripts/check-public.ps1`、`.gitignore`；
  - `docs/releases/`、`docs/RELEASING.md`、`docs/UPDATE_ARCHITECTURE.md`；
  - 以及对应测试。
- **不许碰**：
  - 签名密钥本身和 GitHub 仓库里的密钥；
  - `:hearth`（它仍然不能依赖 `:net`）；
  - 圆桌和炉边的对话逻辑；
  - llama.cpp；
  - `contract/`。
- **禁止操作**：推送、打标签、发布、改 GitHub 设置。

## 验收标准

- [ ] JVM 测试。全部用本机假服务，不连真实 GitHub。测试夹具照真实 GitHub 响应造：真实的 `releases/latest` JSON 形状，真实的跳转链（以步骤 1 实测为准）。
  - **网关下载**：
    - 正常下载；
    - 跳到白名单内；
    - 跳到白名单外被拒，包括第二跳才出白名单的情况；
    - http 跳转被拒；
    - 跳转次数太多；
    - 断点续传，包括续传时重新走跳转；
    - 服务器不支持 Range 时从头下；
    - 取消；
    - 审计内容：有每一跳的域名，没有正文。
  - **发布信息**：按名字找资产、缺 `.sha256`、缺 APK、限流、404、格式不对。
  - **检查节奏**：24 小时内不重复查；忽略的版本不再提示；出了更新的版本再提示；开关关掉后不自动查；调试包不自动查。
  - **校验**：sha256 不对、包名不对、签名不对、versionCode 不比当前大，都拒绝，并删掉文件。
- [ ] 设备测试。用红魔，用手机前先问用户。用调试包，**不碰手机上装着的正式版 0.1.1**。
  - **更新流程**（Compose 设备测试加本机假服务）：
    - 自动检查后出现红点和卡片；
    - 下载进度；
    - 校验通过；
    - 拉起系统安装确认界面，截图到这一步为止；
    - 系统界面上的「安装」由用户点，或经用户同意后由 agent 点；点完确认版本号变了、数据还在。
  - **校验失败**：截图失败时的提示。
  - **升级保数据**：
    1. 用调试签名分别构建 `v0.1.1` 标签和本分支；
    2. 先装旧的，造测试数据；
    3. 再覆盖装新的，确认能打开、数据还在、不用卸载。

    哪些数据，以 0.1.1 实际有的为准，交付报告列出来。如果 `v0.1.1` 用现在的工具链编不出来，写明原因，改用能编出来的最早提交，并说明它和 0.1.1 的数据结构是否一样。
- [ ] 发版检查脚本 `scripts/release-guard.sh`：在本地演示以下各一次「通过」和「中止」：
  - 签名指纹比对；
  - versionCode 检查；
  - 缺发布说明。
- [ ] `scripts/check-public.ps1`：自测通过。对本分支跑一次，结果写进交付报告，只写数量和类别，不写命中的原文。
- [ ] 正式包只含 arm64-v8a 的原生库，交付报告写改前、改后的大小。
- [ ] 在全新 worktree 里，对已提交的版本跑 `scripts/check-all.ps1`，零失败、零警告。

## 发版那天（不在这个包里，由统筹和用户做）

1. 统筹审过以后，合并进本地 `main`。
2. 统筹跑 `scripts/check-public.ps1` 并清理，把会公开的内容清单给用户看。用户同意后才推送 `main`。
3. 看 CI 跑通；手动触发发布流程试跑，确认签名指纹对得上。
4. 用户同意后打标签 `v0.4.0`，看 GitHub 上的发布出来、附件齐全。
5. 手机从 0.1.1 升到 0.4.0：这一次只能走旧路，0.1.1 会用浏览器打开下载地址；也可以用数据线装。
6. 尽快发一个 0.4.1（可以只是小修），在手机上走一遍真正的应用内升级，作为这套更新的最终验收。

## 风险

- **GitHub 在国内可能慢或连不上**：靠断点续传和重试。不加第三方加速地址；以后要加的话单独决定，有 sha256 和签名校验兜底。
- **签名对不上就无法覆盖安装**，只能卸载重装、丢数据。所以发版流程固定了指纹，App 装之前也会比对。
- **GitHub 匿名接口每小时限 60 次**：一天一次的检查远低于这个数。
- **数据库结构变化**：靠「升级保数据」测试兜底。以后每个改数据库结构的包，都要带迁移测试。

## 审核

- 方案审和全量审必做。这个包涉及出网和安装，额度够的话加一轮专项审，审网关重定向白名单、下载校验和安装来源。
- 真机截图交统筹看。
- 通过后由统筹合并进本地 `main`。
