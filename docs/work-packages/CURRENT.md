## 10-24 统筹裁定（生死线没过之后）——已完成，留作记录

夜里的进展很好：4 项 P1 全修，真机复验仍选快变体，门禁 512/0/0。现在唯一卡住的是生死线：温度 0 时开和关检查点的正文不同。

### 一、生死线：先用对照实验分清原因，再按结果修
- **统筹的判断：** 采样器在温度 0 时只有 greedy，没有重复惩罚，可以排除。最可能的是「批次形状」：
  - 开检查点时，从检查点位置起切批；关的时候，从 0 起按 512 切批。
  - 两条路的批次边界不同，矩阵运算的累加顺序跟着不同。循环层的分块扫描也受切法影响。
  - 浮点误差在温度 0 下足以让某个字分叉。这是 llama.cpp 的已知特性，不一定是检查点存错了。
- **第 1 步：对照实验（红魔，按「手机」规矩）。**
  - 关检查点，同一段对话、同一个问题，`n_batch`/`n_ubatch` 分别用 512 和 256，各跑一次；
  - 再加一组：关检查点，但在检查点位置强行切一刀（读到位置 p 先提交，再接着读）。

  判定：
  - **512 和 256 的正文就已经不同**：批次形状坐实，做第 2 步；
  - **两次相同，而「强行切一刀」那组和开检查点那组相同**：同样是批次形状，做第 2 步；
  - **都相同，只有开检查点那组不同**：检查点确实少存了状态。停下第 2 步，先查漏存了什么，候选有循环层的卷积状态、单元位置和序列元数据、输出缓冲。把数据报给统筹。
- **第 2 步：固定的切法（只在批次形状坐实以后做）。**
  - 读提示一律按同一套规则切批：在每一轮「用户消息结束、助手头之前」那个位置（也就是检查点的位置）切开，段内从段首起每 `n_batch` 个一批。
  - 开检查点、关检查点、第一轮，全部用这套规则，并且固定线程数。这样同一个位置上的状态，无论从哪条路算出来都完全相同。
  - 关检查点、整段重读时，要从 token 序列里把以前各轮的这些位置都找出来。
  - JVM 测例：
    - 切法只由 token 序列决定，同样的输入得到同样的切法；
    - 各轮边界都被切开；
    - 开和关的切法在共同前缀上完全一致。
  - 真机：开和关，温度 0，至少 3 轮，**逐字相同**。读提示的速度变化写进交付，应该可以忽略。
- 如果固定切法以后还是不同，不要改验收标准，把数据（第一个分叉的位置、那一步两边的前几个候选和它们的分数）报给统筹，由统筹定。
