# P2-1c 本地对话提速：记住已经读过的上下文，下一轮只读新增的部分

- 仓库 / 基准提交：安卓仓库 `main`（P2-2 合并后）
- 分支：`wp/P2-1c-prompt-cache`
- 工作目录：`D:\Agent\Project\Nivra`
- 依赖：P2-2 已合并。
- 规模：2–4 个工作日。
- 背景：
  - P2-2 真机测速（Qwen3.5-4B，6 线程，红魔）：约 1500 token 的提示，**读提示要 94–110 秒**，生成 148 token 只要 18–21 秒。一问一答两分钟，主要时间花在读提示上。
  - 原因：本地引擎每次生成前都清空上下文缓存（`engine.cpp` 里的 `llama_memory_clear`，见 `llm/README.md`「每次生成先清空 KV」），所以同一段对话的每一轮，都要把人物设定和全部历史从头再读一遍。
  - 同一段对话里，相邻两轮的提示前面绝大部分是一样的，只多了上一轮的回答和这一轮的问题。只要保留缓存，下一轮就只需要读新增的那几十到几百个 token。

## 目标（用户能得到什么）

- 和同一个人物连续聊天时，从第二轮开始，「点发送到开始出字」的等待时间明显缩短：读提示的时间只和新增内容的长度有关，和整段历史的长度无关。

## 步骤

1. **引擎保留缓存**：生成前，拿新提示的 token 序列和缓存里已有的序列比较，保留最长的相同前缀，只删掉后面不一样的部分，再只读剩下的新 token。不再无条件清空。
2. **什么时候必须整段重读**：换模型或卸载；换了对话或人物（用一个「缓存键」区分，例如人物 ID 加会话 ID，测试模式用临时会话 ID）；上下文放不下、从前面截掉了历史（前缀变了）。截断时尽量让人物设定这一段保持在最前面不变，这样至少设定部分不用重读。
3. **接口**：`:model-api` 的生成参数里加一个可选的缓存键。不传时行为和现在完全一样（每次整段读），圆桌和其他调用方不受影响。炉边传人物和会话。
4. **正确性优先**：缓存命中和不命中，在温度为 0 时生成的内容必须完全一样。停止、取消、出错之后，缓存要处在可用状态，或者被明确作废，不能带着半截内容进入下一轮。
5. 引擎的统计里增加「本轮复用了多少 token、实际读了多少 token」，交付报告和真机日志都要记。

## 范围

- **可以改**：`:llm`（含 `engine.cpp`）、`:model-api` 的生成参数、炉边调用处传缓存键，以及对应测试。
- **不许碰**：llama.cpp 源码和固定提交；圆桌的调用（不传缓存键，行为不变）；`contract/`；发布签名；版本号。

## 验收标准

- [ ] JVM 测试（假原生层）：相同前缀被复用；缓存键不同、换模型、截断时整段重读；不传缓存键时行为不变；停止和出错后缓存被作废或保持一致。
- [ ] 真机（红魔，用手机前先问用户）：
  - 用 P2-2 测速用的那段约 1500 token 的对话，连续问 3 轮，每轮记下复用的 token 数、实际读的 token 数、读提示耗时、生成耗时；和 P2-2 的 94–110 秒对比；
  - 温度设为 0，同一段对话分别在「有缓存」和「清空缓存」两种情况下生成，输出逐字相同；
  - 截图：一次第二轮以后的对话（显示等待时间变短）。
- [ ] 全新 worktree 对已提交版本跑 `scripts/check-all.ps1`，零失败、零警告。

## 风险

- 缓存会占内存：8192 上下文的缓存本来就分配好了，复用不额外增加；但要确认长时间多轮对话后内存不持续上涨。
- 如果复用出了错（读到别的人物或别的对话的缓存），模型会答非所问。所以缓存键必须带人物和会话，测试必须覆盖「换人物、换会话」。
