# P2-1d 混合模型的检查点复用：让 Qwen3.5 这类模型也只读新增的部分

- 仓库 / 基准提交：安卓仓库 `main`（P2-1c 合并后）
- 分支：`wp/P2-1d-hybrid-checkpoint`
- 工作目录：`D:\Agent\Project\Nivra`
- 依赖：P2-1c 已合并。排在 P2-5 方案审必修项之后（用户 2026-10-22 定）。
- 规模：3–5 个工作日。
- 背景：
  - P2-1c 做了「复用已读过的上下文」：新提示和缓存比出最长公共前缀，`llama_memory_seq_rm(memory, 0, reuse, -1)` 删掉后面不一样的部分，只读新增的 token。
  - 这个做法对普通结构（纯注意力）的模型有效，但用户手机上用的 **Qwen3.5 是混合状态模型**：
    - 它有一部分是循环层。循环层的状态只有「最新的一份」，不能按位置倒回去，所以 `seq_rm` 会返回 false，P2-1c 就只能整段重读（`reuse_fallback_reason == 3`）。
    - 结果是机制和正确性都交付了，但用户能感觉到的提速，在这个模型上没有。
  - 一个提示约 1500 token，**光读提示就要 94–110 秒**（P2-2 真机测速）。
  - 固定的 llama.cpp 提交 `5e03bdd` 里已经有现成的办法：
    - 接口：`llama_state_seq_get_size_ext` / `llama_state_seq_get_data_ext` / `llama_state_seq_set_data_ext`，配合 `LLAMA_STATE_SEQ_FLAGS_PARTIAL_ONLY`（只存、取「部分状态」，也就是循环层的状态或滑动窗口的那部分），见 `include/llama.h` 第 919–950 行。
    - 参考实现：llama.cpp 自带的 server 用这套接口做了「上下文检查点」，见 `tools/server/server-context.cpp`：
      - 第 2513–2570 行附近：存检查点，带 `PARTIAL_ONLY`，有条数上限和最小间距；
      - 第 3590–3612 行附近：找位置不超过可复用长度的检查点，恢复；找不到就整段重读；
      - 第 3708–3830 行附近：在什么时机存，在「用户这一轮开始」的位置存。

## 目标（用户能得到什么）

- 用 Qwen3.5 和同一个人物连续聊天时，从第二轮开始，「点发送到开始出字」的等待明显缩短。读提示的时间只和「上一轮以来新增的内容」有关，和整段历史的长度无关。
- 回答内容和以前完全一样：温度为 0 时，用检查点和整段重读，输出逐字相同。

## 步骤

1. **先读懂参考实现，再写方案。** 方案里写清楚：
   - 检查点存在哪个位置，以及为什么。
     - 候选一：每轮「用户这一轮开始」的位置（server 的做法）；
     - 候选二：每轮读完提示、开始生成之前的位置。

     关键看下一轮重新拼出来的提示，和上一轮缓存在哪里开始不一样。聊天模板会去掉回答里的思考段之类，所以分叉点往往在上一轮回答的开头附近。**用真实的 Qwen3.5 模板，把连续两轮拼出来的 token 序列对比一次，写进方案。**
   - 恢复的顺序：
     1. 找到「位置不超过公共前缀」的最新检查点；
     2. 用 `set_data_ext(..., PARTIAL_ONLY)` 恢复循环层的状态；
     3. 对注意力层用 `seq_rm(pos, -1)` 删掉检查点之后的部分。要确认恢复以后这一步返回 true；
     4. 从检查点的位置接着读剩下的 token。
   - 任何一步失败，都退回 P2-1c 的整段重读，并给一个新的回退原因码。
2. **只对混合或循环模型启用**：`llama_model_is_hybrid()` 或 `llama_model_is_recurrent()` 为真才走检查点。纯注意力模型照旧走 P2-1c 的路径，行为不变。
3. **检查点的管理**：
   - 跟着 P2-1c 的缓存键走：换人物、换会话、换模型、卸载模型、停止、出错，检查点和缓存一起作废；
   - 每个缓存键最多留几份（先定 3 份，写成常量），总占用设一个上限（先定 256 MB，写成常量）。超了就淘汰最旧的；
   - 在真机上量出一份检查点有多大、存一次和恢复一次各要多久，写进交付报告。阈值按实测调整。
4. **统计和日志**：在 P2-1c 的统计上增加这些项，交付报告和真机日志都要记：
   - 是否从检查点恢复；
   - 检查点的位置；
   - 实际复用了多少 token、实际读了多少；
   - 检查点大小，存和取的耗时；
   - 回退原因。
5. **一个总开关**：在引擎里留一个常量开关，可以一键关掉检查点复用，回到 P2-1c 的行为。真机上的逐字比对（见验收）不通过时，就把开关关上交付，并报给统筹。

## 风险

- **恢复错了状态，模型会答非所问。** 逐字比对是这一包的生死线，必须在真机上用真实模型做，不能只靠假原生层。
- **检查点太大，或者存、取太慢，可能抵消一部分收益。** 用真机实测的数据定份数和上限。
- **聊天模板的分叉点和预想的不一样。** 第 1 步要用真实模板对比两轮的 token 序列，不能凭印象。
