## 第 1 步：网关文件下载（C1；报告第 2 条前半 + 第二节 Q1–Q4/Q6 + 矛盾点表）

**复审原文要点**

1. **`.sha256` 获取路径**：用 `ReleaseInfo.sha256Url` 的 `browser_download_url`，经 `readFollowingRedirects` **逐跳检查**，调用上限 **4 KiB**，独立审计（现有客户端 URL 来源正确）。`C0` 改 PLAN 接口清单及错误域名描述；`C1` 实现通道；`C4` 接线并同步架构文档。
2. **416**：先检查合法 `bytes */N` 且本地长度等于 N：不写文件，交给哈希判断；其他情况重新从原始 URL 发**无 Range 请求**，恢复次数必须有界；补完整、越界、缺失或畸形 `Content-Range`、恢复后仍 416 的用例——「长度相等」不等于内容正确。
3. **跳转计数**：最多五次重定向应固定为「最多联系六个地址」；第六次重定向响应不得导致第七个请求。
4. **异常 206**：PLAN 115、SURVEY 171 所写的「206 起点错误按 200 处理」必须改为**关闭该响应、重新请求完整实体**，不能截断后把错误的局部响应当完整文件写入；异常 206 不写其响应体。
5. **网络重试归属**：统一放 `:net/FileDownloader`，app 不套第二层重试；明确为初次请求之外最多三次网络重试，2/5/10 秒，可取消；哈希失败的全量重下另限一次。
6. **取消**：取消协程时**显式调用 `GatewayCall.cancel()`**，不能以 `scope.cancel()` 代替阻塞 I/O 的取消；文件哈希、重试等待均检查取消；取消后不得有后续请求。
7. **审计**：正常无重试下载有 APK、校验文件**两条**审计；发生重试时不能仍硬断言「总共两条」；被拒域名不进「实际联系过的域名链」，记录失败及已联系的跳，首次即被拒时空链要能表达；**不要把签名 URL 的查询串写入审计**。
8. **`LocalHttp` reason phrase**：只覆盖所需状态码、其他用合法通用短语；保留 `String` 构造兼容性，避免重复输出 `Content-Length`，并回归 `:roundtable:test`。
9. 报告第二节判定：Q3（120 秒停滞检测）**本轮不加**；Q4（If-Range）**本轮不做**，但前提是「期望哈希真正进入重下策略」（见第 4 步）；Q1 的结论如上第 7 点。

**建议做法**：在 `:net/FileDownloader` 定死「逐跳白名单 + 最多六地址 + 有界恢复（416/异常 206）+ 可取消 + 重试」的单一 API，app 只调用不重试；`.sha256` 走同一条 4 KiB 上限通道并单独记审计；把上表的每个上界写成常量并在 KDoc 里指回本清单。

**验收证据**（报告原列）：污染续传恰好重下一次；第二次校验失败删除；取消校验文件读取/哈希/退避后无后续请求；异常 206 不写其响应体；416 正反及循环上界；5 次跳转成功、6 次拒绝；identity 请求头；元数据超限拒绝；并发同文件第二请求立即拒绝。

## 第 3 步：自动检查（C3；报告第 3 条 + Q5 + 隐私页字段）

**复审原文要点**

1. **进程重建**：简报当前定义里成功检查时间被持久化，而 `release` 仅在内存中 —— 发现新版后杀进程、24 小时内重开，会跳过检查且失去卡片，也失去续传目标。需要持久化**可恢复的发布元数据和目标 tag**，启动时恢复并重新核对文件存在性、当前版本及忽略状态。
2. **节流**：简报 301–302「仅成功才更新时间」会使失败后的每次启动都再次请求，与任务书及发布说明「一天最多一次」冲突。按任务书固定**自动尝试**时间节流；需要显示成功时间时另存字段；手动检查不受限。
3. **接口与假断言**：第 3 步先定义下载、校验和安装的完整接口，使用**显式 fake** 测试；检查与卡片测试不因实现尚未完成而成为「假断言」，但**不能靠可空依赖和 TODO 伪造可用下载按钮**；明确 `UpdateCenter` 与 Activity ViewModel 的关系及实际 factory 类型；两个都带默认 `null` 参数的 `MyceliumApp` 重载会使无参调用歧义 —— 保留一个明确入口或同步迁移调用点。
4. **资源**：第 3 步一次加入第 4/5 步尚未使用的全部字符串，与本步「零 `UnusedResources`」的门禁冲突 → 文案键可以先定清单，资源应随使用代码加入。
5. **Q5 注入工厂**：工厂必须在 Activity 启动前替换，并在测试结束恢复；不要只写 `@Before`，应使用包在 Activity/Compose rule **外层的规则或受控启动**；debug 默认禁止自动检查，因此既有测试「必然触网」的说法也过强，仍需**专测非 debug 分支**。
6. **隐私页字段**（与 C1 一起）：显示实际联系过的域名链和本次字节数；旧记录保持单域名、无字节数；失败、续传、未知长度及旧 JSON 均应有显示断言。

**建议做法**：把「上次自动尝试时间（含失败）」「上次成功时间」「忽略的版本」「当前候选发布元数据 + 目标 tag」四个键一次定完并写进架构文档；卡片渲染与检查调度都用假依赖测；对 debug/非 debug 各写一条分支测例。

**验收证据**（报告原列）：进程重建后不重复检查但卡片仍在、同 tag 可恢复；失败后 24 小时内自动请求计数不增；手动仍可查；关闭开关和 debug 不自动查；测试工厂先于 Activity 生效；第 3 步独立编译并通过两种 lint。

## 第 4 步：下载与校验（C4；报告第 2 条后半 + 第 4 条 + Q6/Q7 + 矛盾点表）

**复审原文要点**

1. **接线缺口**：简报 512–516 的 `downloadApk` 没有 `expectedSha256`，而 `FileDownloader` 正是靠该参数决定重下；`fetchChecksumText` 没有 `GatewayCall`，却在 659 行要求使用同一个 call。照此实施，污染的续传文件可能只在最后被删、不会按要求重下；取消也可能停不掉校验文件下载。固定流程：先通过有 **4 KiB 限制**的通道取得期望哈希，再把哈希和**同一取消句柄**传给下载策略；文件哈希、重试等待均检查取消；**完整通过前不得进入可安装状态**。（其余上界见第 1 步第 3、4 点。）
2. **Q6 哈希位置**：网络重试统一进 `FileDownloader`；本轮先采用**下完后整文件流式哈希**，避免续传、截断、重试时重复维护摘要状态；边下边算作为后续优化；**校验器不再重新联网取校验文件**。
3. **Q7 空间（不可接受）**：对约 38 MiB 的包，`max(32 MiB, size/4)` 仍是 32 MiB，没有解决问题。改为按「**剩余下载量＋一份安装会话大小＋余量预算**」，并在建会话前复查；未知大小的 64 MiB 只能是初始门槛；续传不要把已有字节重复算作新增占用；提示明确包含还差多少。修改 `UpdateFiles`、`ApkDownloader` 及架构文档第 4 节。
4. **清理语义**：区分「取消下载保留 `.part`」与「放弃该版本/取消安装删除缓存」，修正文档把所有「用户取消」都归为删除的歧义；清理**不得删除正在使用的文件**；当天 `.part`、过期 `.part`、跨 tag 文件分别测试。
5. **四项校验顺序（按任务书）**：`sha256 → 包名 → 签名 → versionCode`。换序不必然削弱安全性，但会改变首个错误文案；现有 `ApkFactsReader` 又一次读取签名，不能直接证明换序节省成本。若以后改序，必须记录有意偏离及多重错误包的优先级。
6. **签名政策**：App 与当前安装实例比较签名、CI 固定发布指纹的分工可以接受；但「签名相同等价于能覆盖安装」不成立（ABI、版本仍可能阻止安装）；当前单签名政策应**明确拒绝异常多签名**，不能无条件只取 `[0]`；合法签名轮换需要单独设计，现有比较方式并未支持。

**建议做法**：`ApkDownloader.downloadApk(apk, expectedSha256, call)` 一个签名定死「哈希 + 取消句柄」；空间预算用「当前文件已占用字节 + 剩余下载字节 + 会话副本大小 + 余量」函数，未知大小时用 64 MiB 门槛并在拿到长度后与安装前各复查一次；校验器只做本地校验，不再发起网络请求。

**验收证据**（报告原列）：污染续传恰好重下一次；第二次校验失败删除；取消校验文件读取/哈希/退避后无后续请求；异常 206 不写其响应体；416 正反及循环上界；5 次跳转成功、6 次拒绝；identity；元数据超限拒绝；并发同文件第二请求立即拒绝。**另**：72 MiB 场景在下载前拒绝；刚好边界、续传、未知大小、空间途中变化均有测例；建会话前文件缺失/长度改变不继续；四项失败逐项证明未安装且文件已删。

## 第 5 步：安装（C5；报告第 5 条 + Q8/Q9 + 矛盾点表）

**复审原文要点**

1. **删除无效退路**：本机 Android 37 SDK 的 `PackageInstaller.java:2336` 明确写明：调用者 `targetSdk ≥ 35` 时，使用来自 immutable `PendingIntent` 的 `statusReceiver` 会抛 `IllegalArgumentException`；本项目 `targetSdk` 为 37。它不是可以等真机再二选一的路线。方案定为**显式 component ＋ 清单非导出接收器 ＋ `FLAG_MUTABLE`**。
2. **API 用法**：`openWrite` 返回的是 `OutputStream`，应调用 `session.fsync(out)`，**关闭所有写流后**调用 `commit(pendingIntent.intentSender)`；简报的 `fd.sync()` / `commit(pendingIntent)` 不能作为照写代码。SDK 的 `setAppPackageName` 也**没有**简报所暗示的废弃标记，不能用错误的废弃理由要求删除。
3. **可恢复会话状态**：清单接收器能唤起进程，不等于内存里的 `onStatus` 回调还能恢复。持久化 `sessionId`、目标包名/versionCode、tag 和阶段；结果写入可恢复状态，按本应用会话关联、**幂等**消费。回前台版本未变只能说明尚未确认成功，**不能自动判为取消**；成功更新还可能终止旧进程，结果提示和清理应能在新进程完成；前台不在时，也不能假定接收器总能直接拉起确认 Activity。
4. **Q9（不可接受）**：「还是旧版本＋超过 10 分钟」不能证明用户取消或安装失败。依据明确取消、终态结果和本应用持久化的 `sessionId` 清理；超时只能**标记待核实**，不能把未完成安装冒充取消。
5. 会话清理依据、进程死亡后的结果恢复、未知来源返回流程（`Q5`/Q8 结论）。

**建议做法**：先删掉 immutable 动态接收器那条退路和对应文字；会话阶段机（`CREATED → WRITTEN → COMMITTED → PENDING/SUCCESS/FAILED/CANCELLED`）落盘，任何回调都按 `sessionId` 幂等落库，UI 只读落盘状态；`C5` 在同提交里改 Manifest、实现、测试和架构文档第 5 节。

**验收证据**（报告原列）：流关闭/提交顺序测试；显式 mutable 接收器的状态和 Intent extras；进程重建、重复/迟到回调、旧版本仍安装中、明确取消、写入或 commit 异常、只清理所属会话；`lintRelease` 和设备确认界面证据。

### 第 9 步 / R9：修扫描契约（报告第 8 条）

**复审原文要点**

- 原脚本使用 `git ls-files` 后读取**工作树内容**，不是读取 HEAD blob；脏工作树可能把 HEAD 中的内容隐藏掉。改为**扫描明确的 HEAD 内容**，或在脏工作树**直接拒绝**出具门禁结果。
- 历史基准缺失时不得静默缩小范围；报告**基准 SHA、HEAD SHA、提交数和空范围含义**。
- 当前用户名正则的 `[A-Za-z0-9._-]+` 会漏掉以中文等字符开头的 Windows 用户名。修正并保留**不自匹配**的测试。
- 为真实 Git 历史路径补自测，覆盖新增后删除、多 hunk、敏感文件重命名/二进制文件、合并提交、基准回退和空范围。
- 文件名本身若含敏感词，直接打印路径仍可能带出该词，后续应补**文件名脱敏**。
