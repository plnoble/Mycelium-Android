## 做了什么

目标：Qwen3.5 这类**混合/循环模型**上，让同一段对话从第二轮起不再整段重读提示。

1. **整份状态检查点**：读到「本轮用户消息结束、助手头之前」（应用侧算法 `tokenizeBoundary`
   实时计算，不写死常数）就把模型的**整份状态**（含循环层）存为一份快照；下一轮先恢复快照，
   只读新增的 token。恢复用统筹裁定的三步法（清序列 → 整份装回 → 从落点续读）。
2. **固定切法**（逐字一致的前提）：预填批次只在「每条消息结束处」切开（`setCheckpointCuts`，
   由 token 序列唯一决定），段内再按 n_batch 分批；**开、关、第一轮共用同一套切法**，且与
   「这一轮存不存」「落点参数是否为 -1」完全解耦。这样开/关两条路在共同前缀上的批次形状一致，
   温度 0 的 argmax 不会因浮点末位翻转。
3. **CPU 指令集运行时挑选**：编两份原生库——基础版（armv8-a）与快版（armv8.2-a+dotprod+i8mm+fp16，
   自包含、`BUILD_SHARED_LIBS=OFF` 避免符号冲突）。运行时按 `/proc/cpuinfo` 的特性挑：要求
   `asimddp` + `i8mm` + (`fphp` 或 `asimdhp`)，任一不满足自动退基础版；快版加载失败也退。
4. **换键（rekey）**：新会话第一轮用临时键存检查点，拿到正式会话编号后原子地改挂过去
   （迁移成功前不松手，失败回滚源键，`cacheOwner` 迁移成功后才提交）。
5. **字节归原生**：快照字节留在原生句柄表，Kotlin 只存位置/句柄/字节数——JVM 堆零占用；
   分配失败只跳过优化，绝不让生成失败。
6. **内存防线**：每键 1 份、总上限 300 MiB、按插入序号淘汰；`onTrimMemory` 接生产接线
   （明确区分内存压力与 UI_HIDDEN），空闲也能真正清仓。
7. **线程上限**：引擎入口按核数夹住线程数（默认 8），实测超订是灾难性的（10 线程 0.18 tok/s）。

## 已知问题

1. **跨批次形状的浮点差异是 llama.cpp 固有特性**：同一提示在不同批次切分下，温度 0 的 argmax
   可能翻转。统筹已把逐字判据定为「固定切法、固定线程下开/关一致」——已做到；不同 n_batch
   不要求一致（矩阵测例实测 512/256 一致属于这段提示的运气，不是承诺）。
2. **恢复失败的轮次整段重读**（reason=5/6，正确性不受影响）。
3. **「开关关 ⇒ 原因 7」不可达**：编号 7 已从引擎契约废除，接收侧保留宽容以防旧读数。
4. **在途快照瞬时峰值** = 已有句柄 + 一份拷贝；低内存时按准入跳过（`checkpointSkippedForMemory`），
   不代表稳态占用。原生内存峰值观测（PSS）留待后续补。
