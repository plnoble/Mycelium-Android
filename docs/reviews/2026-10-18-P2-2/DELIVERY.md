## 一、这一包做了什么

1. **人物三选一模型**（`:hearth`）：`ModelKind` 三种取值 `default` / `local` / `cloud`，新增
   `model_kind`、`service_id`、`service_name`、`cloud_confirmed_service` 四列；选 `local` 必须带登记里的
   模型，选 `cloud` 必须带云端服务，否则拒绝保存。老库用 `PRAGMA table_info` 查缺列再 `ALTER TABLE`
   补列，老人物原来指向一个具体本地模型，升级时把 `model_kind` 置成 `local`，**一行数据不动**。
2. **预设人物 5 个**：阿远、年糕、老K、外婆、老陈（名字/头像字/头像色/性格/说话方式/背景简介/开场白
   按附录写），第一次打开炉边时写入，写完才落标记；写入用稳定 id + `INSERT OR IGNORE`，所以第一次
   失败可以重试且不会重复；删掉的预设不会自动加回来。每个人物的设定里都带安全兜底句（提示里一定含有、
   编辑页也看得见、可以改），默认用「默认本地模型」，联网搜索保持关闭。
3. **测试模式与沉浸模式**：规则放在模块里（`HearthChat`），测试模式不读库里的历史、不写任何东西
   （`finish` 返回 null、`redo` 返回 false），沉浸模式照旧读写；对话页顶部开关，默认沉浸；测试模式
   顶部写明「测试模式 · 不留记录：不写库、不留历史，离开这页就没有了；也不读不写这个人物的记忆」。
4. **云端走 P1-7 的网关**：`:net` 新增 `GatewayPurpose.HearthChat`（界面标签「炉边聊天」）与
   `HearthChatTest`（「炉边 · 测试模式」）；**记不记正文双重保护**——请求级 `omitAuditBody` 选项，或
   purpose 为 `HearthChatTest`，两者任一成立就不记正文，成功与失败两条审计路径统一；字数、时间、host、
   状态照记。`:roundtable` 的 `CloudChatModel` 增加 `purpose` / `omitAuditBody` / `naturalChat`
   （默认值保持圆桌原样）。`:hearth` 仍然只认 `:model-api` 的 `ChatModel`，云端模型由 app 注入。
5. **隐私可见**：云端人物在人物卡片与对话页都标「云端」；第一次把某个人物切到某个云端服务时弹一次
   说明——「这个人物的聊天内容（以后还有它对你的记忆）会发给「服务名」。确认后才会生效」，确认记住的
   是「已确认过的服务」（换一家服务会再问一次）；每条回答下面标「本机 · 模型名」或「云端 · 服务名 模型名」。
6. **本轮归属快照**：发送瞬间固定人物、模式、会话、问题与解析出的模型；正常完成、停止、取消、
   重新生成都走同一个快照，生成期间切模式/切会话不会把这一轮写到错地方。

## 五、隐私与出网

- **默认本地**：不开云端时不出网；走查里飞行模式下本地模型照常对话（第四节）。
- **云端要逐人物确认**：第一次把某人物切到某服务时弹一次说明，写明聊天内容与记忆会发给哪家服务；
  **取消不生效**（走查验证：取消后云端模型未选中，确认后才选中）。
- **出网只经网关**，用途 `HearthChat` / `HearthChatTest`；白名单按已保存的服务地址放行，
  明文只允许 debug 下的 127.0.0.1。
- **测试模式不记正文**：设备审计实测 `HearthChatTest` 206 字 / 正文长度 0，沉浸模式 `HearthChat`
  377 字 / 正文 377；规则「请求要求不记正文 或 purpose 为 HearthChatTest」对成功与失败两条路径统一，
  字数不变、真正发出去的正文不受影响（有测例）。
- **只发炉边自己的内容**：假服务收到并写进审计的正文只有人物设定（system）+ 该人物的历史 + 当前问题，
  没有圆桌内容（`09-audit-hearth-entries.txt`）。
- **密钥**：界面只显示末 4 位；审计只记 host、用途、字数、状态，不记 headers 与 key（走查与 P1-7 一致）。
- **缺口**（方案审第 4、9 条）：确认状态只绑定「人物 + 服务 id」，同一服务改了 base URL 不会重问；
  审计文件是每实例一份 `AuditLog`，并发完成时可能互相覆盖。两条都在第三节标为未落实。

## 六、已知问题与建议

1. **发送后立刻「停止」会整轮不留**（走查确认）：正文第一个字还没出现时按停止，问题与回答都不进历史，
   界面也没有任何提示（年糕对话里 1.5 秒停止 → 会话只剩开场白）。建议：正文为空时至少把问题留下，
   或给一句中文提示（「这一轮没有产出，要不要把生成长度调大」）。
2. **对话页不会自动滚到最新一条**：新回答写进去了但视图停在原处，要自己往下滑才看得到。
   走查里因此两次误判「消息丢了」，滚到底才看到那一轮其实在。建议新轮次/流式开始时滚到底。
3. **云端回答是整段返回，不是逐字流式**；同步 HTTP 的取消只能取消「收集」，不会中断已经发出的请求
   （方案审第 1 条的未落实部分）。真机上表现为：云端「停止」要等响应回来才生效。
4. **本地模型可能把预算花在隐藏的思考段上**：走查里外婆第二轮观察到约 47 秒没有可见正文才结束，
   期间无法区分「思考段吃掉预算」与「早停丢轮」；建议与 P2-5 的上下文/长度策略一起复验。
5. **走查输入限制**：`adb` 不能注入中文（`input text` 仅 ASCII，英文会被中文输入法当拼音吞掉），
   走查里的中文问题用「拼音 + 候选词」输入，英文问题不可用；这使「恰好停在正文中途」很难命中，
   所以「停止保留已生成部分」只有代码与模块测例保证，没能在真机上截到半句状态。
